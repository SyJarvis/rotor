# 路由与协议转换执行链路

> 更新：2026-09-10（Chat / Responses 完成状态与用量一致性）
> 适用版本：`rotor_gateway 0.5.1`（`src/rotor/`）
> 目标读者：需要理解"一次请求如何被路由到某个渠道、协议如何转换"的开发者

---

## 1. 总览

Rotor 是面向 Coding Agent 的自托管 LLM Gateway，对外同时暴露三种协议端点，对内聚合多种协议的上游渠道。核心问题有两个：

1. **选渠道**：候选里可能有多个不同协议、不同优先级的渠道，按什么顺序试？
2. **转协议**：选中的渠道协议与请求协议不一致时，报文如何转换、损失什么？

一句话结论：

> **常规候选顺序由路由引擎统一决定，发送前还需通过原子准入检查。** 能力过滤（硬性）→ 冷却规避 → 策略排序 → 同协议族优先（软层，可关）→ 会话租约置顶（已到期的故障租约复评除外）。全部渠道冷却时返回暂不可用；冷却到期后通过请求触发恢复探针。已识别、尚无安全转换的请求语义要求对应原生协议；可选 hosted tools 仍允许降级并记录日志。字段保留范围与转换边界见 §4、§6，不保证任意扩展字段无损。

### 请求全链路（ASCII）

```text
客户端 (Codex / Claude Code / OpenCode / API 直调)
   │
   ▼
┌────────────────────────── API 入口 ──────────────────────────┐
│ /v1/chat/completions   → openai_chat                         │
│ /v1/responses          → openai_responses (先转成内部 Chat)   │
│ /anthropic/v1/messages → anthropic_messages                  │
└──────────────────────────────┬───────────────────────────────┘
                               ▼
                 get_available_channels(model, token)
                 enabled + token 允许 + model 匹配
                 (SQL 排序 priority desc, weight desc —— 不看协议)
                               │
                               ▼
              get_session_lease_preference（只读）
                 当前租约 + 故障来源证据 + 固定复评时间
                               │
                               ▼
                    RoutingEngine.route(五步)
   ① 能力硬过滤 (stream/function_call/vision + 原生语义约束)
   ② 冷却/探针占用过滤 (全部暂不可用 → 503 + Retry-After)
   ③ 策略排序 (priority_weighted / fallback_order / weighted / adaptive / affinity)
   ④ 协议亲和分区 (同族在前, 稳定, 可关)
   ⑤ Session lease 置顶 (到期复评且存在可准入同族时跳过)
                               │
                               ▼
              for channel in candidates: 逐渠道尝试
                 admit_attempt（原子检查；冷却到期只准入一个探针）
                 AdapterFactory.create_adapter(channel)
                 (渠道协议 → 选 adapter → 协议转换)
                 成功 → 记账返回
                 可重试失败 → mark_unavailable → 试下一个
                 结束/异常/取消 → release_attempt
```

## 2. 入站端点与请求协议标记

| 端点 | 入口 | `request_protocol` | 备注 |
| --- | --- | --- | --- |
| `POST /v1/chat/completions` | `src/rotor/api/v1/chat.py` | `openai_chat` | `chat_required_capabilities()` 从请求参数、工具历史、图像提取所需能力 |
| `POST /v1/responses` | `src/rotor/api/v1/responses.py` | `openai_responses` | `responses_request_to_chat()` 先归一为内部 ChatCompletionRequest；所需能力由 `responses_required_capabilities()` 计算 |
| `POST /anthropic/v1/messages` | `src/rotor/api/v1/anthropic.py` | `anthropic_messages` | `anthropic_required_capabilities()` 从原始请求的参数、内容块与工具历史提取所需能力 |

`request_protocol` 的用途：

- **路由软分层**的判据（第 4 步协议亲和，见 §4）；
- 写入 `routing_decisions` / `request_attempts` / `usage` 做观测归因；
- **不参与**能力过滤（能力过滤用的是"渠道协议 vs 所需能力集合"，见 §4）。

Chat 和 Anthropic 的能力提取函数位于 [gateway/capabilities.py](../src/rotor/gateway/capabilities.py)，Responses 的函数位于 [adapters/protocol/responses.py](../src/rotor/adapters/protocol/responses.py)。三个入口均将所需能力交给路由引擎。

Codex 关键点：Responses 请求携带原生 `reasoning`、非空 `include`、原生 item、background、结构化输出等语义时会要求 `responses_native`。文本、普通 function tools 和 URL 图像存在转换路径，但图像仍要求 `vision`，工具调用与历史结果仍要求 `function_call`。

### Anthropic 模型发现与 Token 计数

| 端点 | 行为 |
| --- | --- |
| `GET /anthropic/v1/models` | 必须通过 Rotor Bearer / `x-api-key` 鉴权；仅列出启用且 token 可访问渠道的本地逻辑模型，详见下文 |
| `POST /anthropic/v1/messages/count_tokens` | 同样鉴权；优先选择实际支持原生计数的 adapter，无原生计数能力时才估算，见 §8 |

[anthropic_models.py](../src/rotor/api/v1/anthropic_models.py) 返回 Anthropic 目录形状：`data` 中包含 `id`、`type="model"`、`display_name`、`created_at`，分页元数据为 `first_id`、`last_id`、`has_more`。模型集合是 `channel.models` 与 `model_mapping` 的键，去重后按逻辑 ID 排序；不会额外加入映射值、渠道密钥或上游全量目录，原生与可转换渠道均可贡献模型。短期冷却不隐藏已配置模型；`allowed_channels` 的空列表沿用现有“不额外限制”语义。

`limit` 默认 20，范围 1–1000；`after_id` / `before_id` 分别取紧邻后页 / 前页，`has_more` 按请求方向计算。两个游标不能同时提供，不可见模型与不存在模型的游标均返回相同的 400 错误。这里没有已知的上游发布时间，因此 `created_at` 固定为 epoch，不冒充渠道配置创建时间或模型新旧顺序；该未知日期表示法符合 [Anthropic Models API](https://platform.claude.com/docs/en/api/models/list)。读取此目录不发起上游请求或生成。

## 3. 候选渠道生成（协议无关）

`src/rotor/core/deps.py::get_available_channels`：

1. `Channel.enabled = true`；
2. token 配置了 `allowed_channels` 时取交集；
3. `model` 命中 `channel.models` 或 `channel.model_mapping`；
4. SQL 排序 `priority DESC, weight DESC`（仅作为后续排序的输入顺序，不决定最终顺序）。

**这一步完全不看协议**。协议的介入全部发生在 `RoutingEngine` 与 `AdapterFactory`。

## 4. RoutingEngine.route 五步流水线

代码：`src/rotor/gateway/routing.py::RoutingEngine.route`

### ① 能力硬过滤

`_supports_capabilities(channel, required)`：

- `required` 为空 → 全部通过；
- `responses_native` ∈ required → 渠道协议必须是 `responses` / `openai_responses`，否则直接淘汰；
- `openai_chat_native` ∈ required → 必须实际使用 Chat 上行：排除 Responses / Anthropic 协议和 `type=anthropic` 的渠道；
- `anthropic_native` ∈ required → 必须使用原生 Messages 上行。除 Anthropic 协议外，也允许未配置 Responses 协议的 `type=anthropic` 或 Zhipu 渠道；Zhipu adapter 收到 `anthropic_payload` 时会切到原生 Messages 路径；
- `reasoning_effort` ∈ required → 允许 Chat 原样发送，或 Responses 映射为 `reasoning.effort`；排除尚无映射的 Anthropic 上行；
- Anthropic 请求的非空 `stop_sequences` → 要求 `stop_sequences` 能力，直接排除 Responses 族，因为现有 Chat→Responses 映射不能保留停止序列；Chat 的 `stop` 与原生 Anthropic 的 `stop_sequences` 路径保留。显式能力配置或 lease 均不能绕过这一协议限制，空列表不触发；
- 渠道协议为 Responses 族 → 保留已有兼容特例：自动隐含 `stream` + `function_call`，即使 `extra.capabilities` 是缺少这两项的显式允许表；`vision` 不在该特例内；
- 其余所需能力对照 `channel.extra["capabilities"]` 允许表；未配置视为不限。

原生约束是协议判断，不能通过在 `extra.capabilities` 中声明同名能力绕过。当前提取范围：

| 入口 | 触发原生约束的已识别语义 |
| --- | --- |
| Chat | `response_format`、`parallel_tool_calls`、`max_completion_tokens` 任一非 `None`，或历史消息的 `reasoning_content` 非 `None` → `openai_chat_native`；`False`、`0`、空字符串不会因真假判断被漏掉 |
| Anthropic | `thinking`、`top_k`、`context_management`、`output_config` 非 `None`；显式 `disable_parallel_tool_use`；`document`、thinking 等不可表达内容块；非文本工具结果、工具结果 `is_error=true`、不支持的图像引用 → `anthropic_native` |
| Responses | 状态链、conversation、background、非空 reasoning/include、原生 item、不可转换内容块；`text` 除空值或单纯 `{"format":{"type":"text"}}` 外的设置；`parallel_tool_calls=false`；非默认 truncation、max_tool_calls、store=true、非默认 service_tier；要求 hosted tools 的 tool_choice → `responses_native` |

这些约束覆盖当前明确识别的字段和内容形状，不等同于任意未来协议扩展都已检查。无兼容候选时入口返回 503，不会向被过滤的渠道发送请求。

### ② 冷却过滤与发送前准入

实现：[gateway/routing.py](../src/rotor/gateway/routing.py)、[core/exceptions.py](../src/rotor/core/exceptions.py)。

- `mark_unavailable(model, channel, seconds)` 按 `(model, channel_id)` 记录冷却截止时间与故障代次。新的较短等待时间不会缩短已有冷却；较新的失败也不会被先前请求的成功清除；
- 冷却未到期或已有恢复探针占用时，渠道不进入常规候选。全部兼容渠道暂不可用时返回 `503 / channels_temporarily_unavailable` 和 `Retry-After`，不再重新尝试完整兼容集；
- 冷却到期不代表已恢复。`route()`、`diagnose()` 和租约复评的候选检查只读；真正发送前调用 `admit_attempt()`，对同一进程内的同一 `(model, channel_id)` 最多准入一个恢复探针。这样多个请求即使拿到同一份过期候选，也不能同时探测；
- 恢复探针由下一次业务请求触发，没有定时后台探活。上游成功且未出现更新的故障代次后恢复普通准入；失败或取消则释放探针占用并重新冷却。正常健康渠道不受这个单探针限制；
- 默认冷却 30s，可由 `extra.fallback_cooldown_seconds` 覆盖。所有允许 fallback 的 HTTP 错误均解析 `Retry-After`：支持非负有限数字和 HTTP 日期；过期日期按 0 秒处理，非法、负数或非有限数字回退到渠道默认值。冷却截止时间使用单调时钟；
- 返回客户端的 `Retry-After` 向上取整且至少为 1 秒。探针占用期间若又有已知冷却截止时间，仍保留相应的剩余等待时间；没有剩余冷却时的 1 秒仅是重试建议，不是探针占用的过期时间；
- 候选生成后仍可能被其他请求占用，所以四个生成入口及 Responses `input_tokens` / `compact` 在发送前再次准入。若没有实际尝试就失去所有候选，也返回暂不可用错误。

非流式入口在 `finally` 释放准入；流式通过 [AdmissionStreamingResponse](../src/rotor/gateway/streaming.py) 覆盖整个 ASGI 响应生命周期，处理流未开始消费、发送失败、断连与取消时的占用释放和资源关闭。

### ③ 策略排序

`routing.strategy`（`~/.rotor/settings.json`，pydantic 校验）：

| 策略 | 行为 |
| --- | --- |
| `priority_weighted`（默认） | 逐优先级层内加权随机全排列（LoadBalancer 反复抽取并标记） |
| `fallback_order` | priority desc，同层按 id 升序（确定性） |
| `weighted` | 忽略优先级，纯加权随机全排列 |
| `adaptive` | ML 分数（success/latency/cost/load）排序，**永不跨优先级层**；affinity 仅作 tie-breaker |

传入 `affinity_key` 时，`priority_weighted` 使用保留优先级层的 `_affinity_order`，`weighted` 使用不保留优先级层的该排序。`fallback_order` 仍按 priority/id 排序；`adaptive` 仅在同分时使用 affinity 排位。

adaptive 的延迟样本来自当前 `AttemptContext.elapsed_ms()`，不包含先前渠道的失败等待；用户可见的请求总延迟仍单独保留。背景 Responses 的接受请求可记录一次尝试结果，后续用量轮询没有新的生成尝试，不重复更新该评分或扣减其他请求的 inflight。见 [gateway/accounting.py](../src/rotor/gateway/accounting.py)、[gateway/attempts.py](../src/rotor/gateway/attempts.py)。

### ④ 协议亲和分区（2026-09-10 新增，软层）

```python
family = protocol_family(request_protocol)   # openai / responses / anthropic
ordered = [同族渠道按原顺序] + [异族渠道按原顺序]
```

- `protocol_family()` 归一化：`openai`→openai、`responses|openai_responses`→responses、`anthropic|anthropic_messages`→anthropic、未知→openai；
- **稳定分区**：两组内部保持第 ③ 步的策略顺序，不重排；
- 开关：`routing.protocol_affinity_enabled`（默认开启），关闭后保留策略排序与 lease 置顶，不再进行协议分区；三个入口均采用引擎返回的候选顺序，Responses 入口不再另做 native 优先排序；
- 效果：一个 `openai_chat` 请求，即使某 Anthropic 渠道 priority 更高，也会排在兼容的 OpenAI 族渠道之后（lease 可覆盖此顺序）；同协议可减少转换带来的语义损失风险。

> 设计动机：协议转换（尤其是 Chat↔Anthropic、Chat↔Responses）会丢失或重构部分语义（reasoning 明细、缓存断点、工具命名空间），能用原生协议就该优先用原生协议。它是**软**的：异族渠道仍保留在候选里作为 fallback，而不是被过滤。

### ⑤ Session lease 置顶

- 正常情况下，`preferred_channel_id`（`session_leases` 表给出）若仍在候选中，提到首位并记录 `lease_used=True`。硬能力与冷却准入始终优先；
- [get_session_lease_preference](../src/rotor/services/session_leases.py) 只读租约。仅当前租约为异族、存在可准入的同族替代且复评开启时，才额外查询来源事件；无同族替代时保持原租约，不查询事件历史或写检查点。同族的到期空闲探针属于可准入候选，尚不代表上游已恢复；
- 复评默认间隔为 `routing.session_lease_reassess_seconds=300`；0 关闭。affinity、session lease 或 protocol affinity 关闭也不执行复评；
- 先取最新 `assigned` / `migrated` / 明确的复评检查点，再核对对应成功 `RequestAttempt`，不能跳过缺少证据的新事件而复用旧事件。成功 attempt 的请求协议族必须与当前请求相同、上游协议族必须为异族，且来源满足以下之一：`attempt_index>0`；事件为 `migrated / leased_channel_unavailable` 且确有不同的前渠道；事件为 `renewed / protocol_reassessment_deferred`；
- 复评时间以该事件 `created_at + interval` 为准。普通成功续租只更新 idle TTL，不滑动重置复评时间。到期且路由时仍有可准入同族候选，临时取消 lease 置顶，让同族先尝试；
- 同族成功迁移记录 `protocol_recovered`。复评后仍由原异族渠道成功，写一次 `renewed / protocol_reassessment_deferred`，将下一次复评推迟一个间隔；普通续期不写此事件。写入前刷新锁定租约，迟到的旧渠道结果不能用 deferred 原因抢回已迁移的租约；
- `previous_response_id` 的状态绑定分支不读取复评 preference、不重新选渠道；绑定渠道的请求仍须通过发送准入，不能借复评或 fallback 换到其他渠道。

**五步叠加后的最终优先级**（硬 → 软）：

```text
状态绑定 previous_response_id（直接钉回原渠道，跳过重选，仍受发送准入约束）
  > ① 能力与原生语义硬过滤
    > ② 冷却与恢复探针准入
      > ⑤ session lease 置顶（到期复评且有可准入同族时除外）
        > ④ 协议亲和（同族在前）
          > ③ 策略排序（priority → weight → adaptive/affinity）
```

## 5. 渠道协议 → 适配器选择

路由只决定**顺序**；每个渠道真正怎么发请求由 adapter 决定。代码：`src/rotor/adapters/factory.py::AdapterFactory.create_adapter`

```text
channel.protocol ∈ {responses, openai_responses}   → OpenAIResponsesAdapter
channel.protocol ∈ {anthropic, anthropic_messages} → AnthropicAdapter
否则                                                → 按 channel.type 查表
  openai/deepseek → OpenAIAdapter, azure → AzureOpenAIAdapter,
  moonshot/minimax/zhipu/kimi → 各自 Provider Adapter
```

渠道协议的主要取值为 `openai`、`openai_responses`、`anthropic`，适配器也识别上表别名。协议选择默认生成路径 `/chat/completions`、`/responses`、`/messages`；**鉴权不能只按协议判断**。[provider_defaults](../src/rotor/channels/presets.py) 保留供应商的默认认证，再由 `extra.auth_type` / `extra.headers` 及 adapter 的头部处理决定实际请求。例如 Zhipu 使用 Anthropic 协议仍默认 Bearer，Anthropic 供应商默认 `x-api-key`。

### 渠道管理：目录探测与表单草稿

[channels.py](../src/rotor/api/admin/channels.py) 的 `_fetch_model_list()` 支持 OpenAI 风格的 `data` / `models` / 顶层列表，以及 Anthropic `has_more/last_id`、智谱 `hasMore/lastId` 分页。后续请求只在同一配置 URL 上更新 `after_id`，保留自定义 URL 原有查询参数，不采用上游提供的任意 next URL。全部页成功后才去重排序；游标重复或缺失、后续 HTTP/解析错误、超过 100 页或 10,000 条原始条目均整体失败，不返回可用于覆盖配置的部分结果。HTTP 200 的业务错误和畸形目录不算成功，显式空列表仍是合法目录结果。

- `POST /api/admin/channels/{id}/probe-models` 无 body 时使用保存的配置；带可选草稿时仅接受连接配置覆写，使用保存的密钥探测当前 `base_url/type/protocol/extra`，不写回渠道。响应只有模型、数量与延迟，不回传密钥或配置；替换密钥走 `/api/admin/channels/probe-models` 的未保存探测路径；
- [channel-form.js](../src/rotor/frontend/channel-form.js) 根据服务端 presets 与所选协议计算默认值，保存和探测复用连接参数。编辑旧渠道缺少路径/认证配置时不再硬编码 Chat 默认；切换 provider 或协议仅迁移空值与旧默认，自定义路径、认证方式及额外 headers 保留；
- Anthropic 标准 models/messages 路径经 `join_api_url()` 归一到版本根：未带版本时自动 `/v1`，已带版本或操作后缀时避免重复拼接；显式版本、自定义路径/完整 URL 仍按既有规则处理。此归一发生在发请求时，不重写保存的 base URL；
- 管理页默认“测试”仅执行模型目录 GET，成功提示为“模型目录可访问（未验证生成）”。只有显式指定 `capability=text|stream|function_call` 的 API 测试才会调用生成，可能计费；目录成功不能证明生成能力正常。

## 6. 协议转换矩阵

入口协议（行）× 渠道协议（列）：

| 请求 ↓ 渠道 → | openai | anthropic | openai_responses |
| --- | --- | --- | --- |
| **openai_chat** | 按已建模字段构建 Chat 请求 | OpenAI→Anthropic（`adapters/protocol/converter.py`：消息、工具与响应 usage 转换） | Chat→Responses payload（`adapters/protocol/responses.py`），流式回程再重组 |
| **openai_responses** | 能力允许时转 Chat | 能力允许时转 Anthropic | **native 转发**：保留原生 payload 字段，应用模型映射等上行处理；下行保留 SSE 事件语义 |
| **anthropic_messages** | 能力允许时 Anthropic→OpenAI；Zhipu 可走原生 Messages 例外 | 保留原生 payload，应用模型映射与头部处理 | 能力允许时转 Responses |

Chat 同协议保留的是 [ChatCompletionRequest / ChatMessage](../src/rotor/schemas/request.py) 已建模的字段。`reasoning_effort`、`response_format`、`parallel_tool_calls`、`max_completion_tokens` 在 [OpenAICompatibleAdapter.prepare_request_body](../src/rotor/adapters/base.py) 统一加入实际 HTTP 请求，覆盖各 provider 自行实现的 `convert_request`；历史 `reasoning_content` 随消息发送。未知顶层字段仍由 schema 忽略，内部 `anthropic_*` / `responses_*` payload 和缓存提示不写入通用 Chat 请求。模型映射仍生效；流式请求仍请求 usage chunk，Zhipu 保留其移除 `stream_options` 的兼容处理。

Chat→Anthropic 的 `tool_choice="none"` 通过不发送本轮工具定义保留禁止调用要求，历史 `tool_use` / `tool_result` 不删除。

流式回程转换：

- 非 native 渠道服务 openai_responses 请求时，`ResponsesStreamTransform`（`api/v1/responses.py`）把 Chat chunk 重组为 Responses 语义 SSE。`length` → `incomplete` / `max_output_tokens`，`content_filter` → `incomplete` / `content_filter`，终态事件为 `response.incomplete`；非流式返回相同终态语义；
- Chat 的 `refusal` 保留为 Responses refusal 内容块，流式产生 `response.refusal.delta/done`；字符串 `reasoning_content` 映射为 reasoning item 的 `content` 中 `type="reasoning_text"` 的内容块，流式产生 `response.reasoning_text.delta/done`，不会把原始推理写成 summary；其他未映射的 reasoning 结构显式失败。非流式客户端转换结果也在成功记账前校验，不能将转换失败记为上游成功；已知失败用量的观测与收费边界见下文；
- native Responses SSE 经解析、记账和 JSON 序列化后发送，正常事件保留原生字段；`error` / `response.failed` 仍按现有 adapter 行为规范化为错误。不保证所有原始终态字段、字节、空白或 SSE 帧格式不变；
- Anthropic 原生 SSE 由 `AnthropicAdapter` + `anthropic_integrity.py` 校验，`StreamingUsageAccumulator` 归一 usage 后记账；完整性与归档边界见下文；
- 空流保护：Chat 流处理在未产生 meaningful output 前保留同渠道单次透明重试，第二次仍为空才失败；只有 role/finish 而无输出、无显式 usage 的流仍走该保护，真实终态不能替代非空检查。显式零 usage 加真实终态可成功；已产生输出后不透明重放。原生 Responses 流不做这类透明重试。

usage 记账：所有形状（OpenAI/Anthropic/缓存细分/5m+1h 窗口）统一经 `accounting_service.extract_usage` + `StreamingUsageAccumulator` 归一入库；无 usage → `missing`，绝不估算。

### Chat / Responses 完成校验与用量状态

实现：[openai_integrity.py](../src/rotor/adapters/protocol/openai_integrity.py)、[Responses adapter](../src/rotor/adapters/protocol/responses.py)、[Chat 入口](../src/rotor/api/v1/chat.py)、[Responses 入口](../src/rotor/api/v1/responses.py)。HTTP 200 的业务 error、畸形 JSON 或缺失完成结构不能包装成空成功。Chat 非流式校验所有 choice；流式在原有空流流程后检查所有请求的 choice 都有真实 `stop/length/tool_calls/content_filter/function_call` 终态。普通 error、部分输出后 EOF、未知 finish 均不能补造 `[DONE]` 或 `response.completed`，也不写成功 attempt、成功租约或恢复成功。

Chat 上行的 Base 派生路径及 Kimi / MiniMax 使用严格 SSE 解析，接受无空格 `data:` 和多行 data，坏 JSON 不再静默跳过；这不等于所有语义都有跨协议映射。工具 arguments 仍作为模型输出字符串保留，不因其不是合法 JSON 就一概判 Chat 协议失败，实际执行工具前仍需校验参数。

原生 `POST /responses` 的 adapter 验证完成对象与真实终态，读完上游后才交出 `completed/incomplete` 终态。`incomplete` 是合法协议结果，保留原 response id、status、output、usage 和归档；转成 Chat 时，`max_output_tokens→length`、`content_filter→content_filter`，与反方向映射一致。未知 incomplete 原因在转 Chat 时明确失败。已启动流的错误使用失败事件；不能再发送成功终态，原生错误事件延续已知 response id 与事件序号。

[AccountingService.record_failure](../src/rotor/gateway/accounting.py) 可记录已验证的上游 usage：日志与 ledger 仍为 failed，但保留已知 token 数；未知用量仍标 missing，不补估算。失败用量仅用于观测，沿用不扣 token counter / quota、不计算价格、不续成功 lease 的策略，不把“供应商可能产生用量”误当作协议成功。完整性错误保留实际上游 HTTP 状态（可能为 200），非流式客户端通常收到 502；HTTP 200 中明确的 overload 仍走已有非流式 fallback。

后台 native `queued/in_progress` 接受请求保留上游所有权，无论是否带中间 usage，都不提前生成成功用量账本，绑定记录的 `usage_accounted` 保持 false；返回客户端的中间 usage 仍保留。后续轮询仅对 `completed/incomplete/failed/cancelled` 的有效用量做一次原子 `usage_accounted` claim：前两者记成功，后两者记失败；无用量或非法用量的失败不 claim。`queued/in_progress` 轮询同样不结算；轮询不生成新的 adaptive 尝试样本。

### Anthropic 回程的完整性与显式转换边界

实现：[anthropic_integrity.py](../src/rotor/adapters/protocol/anthropic_integrity.py)、[Anthropic 入口](../src/rotor/api/v1/anthropic.py)。HTTP 200 不等于有效完成：非流式必须有合法 native Message 或可转换的 Chat completion，业务 error、畸形 JSON、缺少终态和无效工具参数不能记为成功。合法的空内容、零 Token、明确终态仍可成功，不以“有文本”代替完整性判断。

原生 SSE 支持多行 data 与事件类型检查，验证 `message_start` → 内容块 start/delta/stop → `message_delta` → `message_stop` 生命周期。工具参数增量必须闭合为 JSON 对象；缺终态、未闭合块或类型冲突会失败。归档重建完整 Message，包括 text、thinking/signature、工具输入、stop 信息及 usage；未知 native 块保留原字段，未知扩展事件或增量保留到 `stream_extensions`，不凭空定义合并语义。下行正常事件保留字段并重新序列化，不保证原始 SSE 字节、空白或帧格式不变。

完整流通过校验并完成记账、提交归档任务后，才向客户端发送成功的 `message_stop`。已经开始的流遇到错误发 `event: error`，不补造成功终态或换渠道拼接内容；错误分类与非流式一致。取消仍结束为 cancelled 并释放资源，不宣称生成成功。

通过 OpenAI 兼容上游返回 Anthropic 的路径同样不能吞掉坏数据：Base 派生 adapter、Kimi、MiniMax 使用严格 SSE 解析，接受 `data:` 后无空格、多行 data，但坏 JSON 不能被后续合法 finish 掩盖；Kimi 也不再把原始错误体包装成空的成功 completion。Chat / Responses 入站的基础完整性校验见上一节；Anthropic-bound 仍额外检查目标协议的工具 JSON 与不可表达语义，不能把这些额外限制推广到普通 Chat 模型输出。

当前明确处理的跨协议语义如下，不能推广为所有未知扩展均无损或均已拒绝：

| 上游 → 客户端 | 已识别边界 |
| --- | --- |
| Anthropic → Chat | thinking 文本在流式/非流式进入 `reasoning_content`，但 signature 不保证能回放；`redacted_thinking` 无安全映射，明确失败。原生 Anthropic 路径仍保留这些块 |
| Chat → Anthropic | 非空 `reasoning_content` / `refusal` 明确失败，不伪造无签名 thinking；终态仅映射 `stop→end_turn`、`length→max_tokens`、`tool_calls→tool_use`，`content_filter`、未知或缺失终态均失败，不推测 `stop_sequence` |
| Responses → Anthropic | 在 Responses 报文变成内部 Chat 前拒绝 `incomplete/failed`、reasoning/refusal、非 message/function_call 输出项及不支持的 message 内容；完整终态须有 `status=completed` 和 output 列表。这些目标协议语义限制仅作用于 Anthropic 入站；基础错误与完成校验则也覆盖 Chat / Responses 客户端 |

### 语义损失清单（为什么要同协议优先）

| 语义 | openai_chat | anthropic | openai_responses |
| --- | --- | --- | --- |
| reasoning 明细/加密项 | 已建模 `reasoning_content` 可原生发送；跨协议受 guard 限制 | thinking 等输入要求原生 Anthropic；回程跨协议的文本/signature/redacted 边界见上表 | **原生保留**；Chat 回程仅已映射字符串 reasoning_content，其余结构显式失败 |
| `previous_response_id` 状态链 | 不适用 | 不适用 | **原生保留**（且钉回原渠道） |
| hosted tools（web_search 等） | 转换时仅保留 function tools | 转换时仅保留 function tools | 原生支持；可选 hosted/namespace tools 允许转换时省略并记日志，强制选择这些工具时要求原生 |
| 显式缓存断点 | 不保证任意缓存扩展透传 | 原生保留 cache_control；转换到 Responses 时仅映射已支持形状 | 原生字段与内部提示按 adapter 规则构建；不支持 prompt_cache_breakpoint 时可摘除后同渠道重试一次 |

## 7. 失败处理与 fallback

代码：`gateway/fallback.py::should_fallback` + `core/exceptions.py`

- 可 fallback 状态码：`401/402/403/404/408/409/425/429/5xx`；
- 触发后先调用 `mark_unavailable()` 记录冷却（已解析的 `Retry-After` 优先），再持久化失败事实并尝试下一个获准入的候选；attempt 记录 `success` / `failed` 等 outcome，成功更新 lease 时使用 `fallback_success` 等成功或迁移原因；
- 不可重试错误（如 400 语义错误）直接抛给客户端；
- 无法保真的已识别转换语义或不完整响应使用 `UpstreamProtocolError`，归类为 `upstream_invalid_response`，通常 HTTP 502，不透明重试或 fallback；已经开始的流通过 error 事件结束。上游明确 overload/rate-limit 另按可用性错误处理；
- 特例：上游以 400 `invalid_parameter` 报"不支持 prompt_cache_breakpoint"时，Responses 适配器会在**同渠道**深拷贝请求、递归摘除断点字段后重试一次（有界兼容重试，不是通用重试循环）；
- 已实际尝试且所有渠道失败 → `All channels failed`（状态码按最后错误分类）；兼容渠道全部处于冷却或探针占用状态、没有获准尝试时 → `503 / channels_temporarily_unavailable`，带建议重试时间。

Anthropic 路径统一使用 [anthropic_errors.py](../src/rotor/core/anthropic_errors.py) 的 `{"type":"error","error":{"type":...,"message":...},"request_id":...}` 外壳，覆盖鉴权、HTTP、参数校验、上游及意外错误。参数校验保留 HTTP 422，但不回显校验输入；上游 HTTP 错误不回传原始响应正文，`Retry-After` 按已有响应头保留。进入 Messages 处理后的错误 ID 与 attempt 的 request ID 同源；上游实际 HTTP 200 与客户端因完整性失败收到的 502 分别保留，不混为一个状态。其它协议路径保留原有错误处理形状。

## 8. 绕过常规路由的特殊路径

| 路径 | 行为 |
| --- | --- |
| `previous_response_id` 有状态请求 | 从 `response_routes` 找到原渠道并校验归属/允许表，**只用该渠道**；跳过常规路由与 lease 复评，但仍须发送准入。记录 `state_binding` 原因，暂不可用时不迁移状态链 |
| `GET/DELETE/POST /responses/{id}[/cancel|/input_items]` | 钉回原渠道的 native Responses adapter（检索/删除/取消/列出输入项）；终态用量按状态幂等记账。GET stream 仍为原始 relay，并未复用 POST 生成流的完整性校验 |
| `POST /responses/input_tokens`、`POST /responses/compact` | 硬性只走 native Responses 渠道（`required_capabilities={"responses_native"}`）；每次调用均检查发送准入并在结束时释放 |
| `POST /anthropic/v1/messages/count_tokens` | 从已启用、token 可访问且模型匹配的渠道中，按 adapter 实际可调用的 `count_tokens` 能力选择（含 Zhipu 原生 Messages 例外），再执行路由、发送准入、可重试故障切换与释放 |

Anthropic 计数返回 `X-Rotor-Token-Count-Source: provider|estimated`：原生结果必须是非负整数 `input_tokens`；只有根本不存在原生计数候选时，才按序列化请求的 UTF-8 字节数提供确定性估算。原生计数失败、被冷却或初始化失败不偷偷退回估算。计数不写生成 usage、不续租或复评租约、不训练 adaptive；也不把计数成功当作生成恢复的证据，所以恢复探针释放后仍按冷却规则等待。此估算仅用于上下文计数响应，与生成 usage 的“不估算”原则不同。

Responses GET stream 的 relay 只旁路提取终态供记账，不能据此宣称其具有 POST 路径的坏帧、截断或完整生命周期校验；原始事件已经发出后也不能由后续记账校验撤回。

## 10. 可观测性

- `routing_decisions`：request_id、request_protocol、策略、required_capabilities、affinity_used、最终候选序；feature snapshot 的 `session_lease.reassessment_attempted` 表明本次排序是否让同族先于原租约；
- `request_attempts`：每次 attempt 的渠道、协议、`outcome`（`success` / `failed`）、`error_category` 等错误事实；`fallback_success` / `leased_channel_unavailable` / `protocol_recovered` / `protocol_reassessment_deferred` / `request_success` 属于 lease 更新的成功或迁移原因。复评检查点留在事件明细，但不计入原有续租活动与迁移率分母；
- `RoutingEngine.diagnose(channels, model, required)`：逐渠道给出 `disabled` / `capability_mismatch` / `cooldown` / `recovery_probe_inflight` 原因、`recovery_probe_eligible` 与 adaptive 分数；`routable` 不再将冷却或占用中的渠道标为可路由；
- 全部兼容渠道暂不可用时，`503` 的错误码与 `Retry-After` 区分于“没有满足能力的渠道”；
- 响应头：`set_routing_headers` 回写 `X-Rotor-Channel`、`X-Rotor-Provider-Model`；发生 fallback 时增加 `X-Rotor-Fallback: true`，没有 attempt 序号头。
- Anthropic Token 计数额外返回 `X-Rotor-Token-Count-Source`，区分原生计数与估算；模型发现不调用上游，也没有生成渠道成功归因。
- Responses 转换到非 native 渠道并省略可选工具时：warning 日志事件 `responses_protocol_downgrade`，包含 `request_id`、`channel_id`、`target_protocol`、`omitted_tool_types`、`reason`；目前没有降级策略配置开关。

## 12. 常见问题排查

| 现象 | 先查 |
| --- | --- |
| Codex 报 503 "No native Responses channel" | 渠道 `protocol` 是否设为 `openai_responses`、`request_path` 是否 `/responses`（部署库配置，不随代码走） |
| 请求总走 anthropic 渠道而非 openai | 全局 `routing.protocol_affinity_enabled` 是否关闭？渠道 family 是否被误配（如 protocol 留空归为 openai）？是否受能力过滤或 lease 影响？ |
| 同协议渠道没有被优先 | lease 是否钉在异族渠道（lease 优先于软层）；`routing.protocol_affinity_enabled` 是否为 false |
| 原生恢复后仍走异族 lease | 复评是否关闭或未到期；同族是否通过能力与准入检查；最新归属事件是否有可靠的跨协议故障来源证据；是否是 `previous_response_id` 状态绑定 |
| 503 带 `channels_temporarily_unavailable` | 查看 `Retry-After`、渠道冷却截止时间与 `recovery_probe_inflight`；请求触发恢复探针，没有后台探活 |
| Responses 原生 reasoning 请求落到 Chat 渠道 | 非空原生 `reasoning` 应触发 `responses_native`；核对 `responses_required_capabilities`。Chat 自身的 `reasoning_effort` 则允许 Chat 或 Responses 上行 |
| 某渠道长期不被选中 | `diagnose()` 看 cooldown / capability_mismatch；`extra.capabilities` 允许表是否漏了 `stream` |
| 目录探测成功但生成失败 | 默认管理页测试仅验证模型目录；检查实际生成路径、认证方式和模型支持，不把目录可访问当作生成通过 |
| Anthropic 模型目录缺少某个模型 | 检查 Rotor 鉴权、enabled / allowed_channels、`models` 与映射键；上游映射值不会被自动额外公开 |
| Anthropic count_tokens 返回估算 | 查看 `X-Rotor-Token-Count-Source`；只有无原生计数 adapter 时估算，原生失败应显示错误而不是 estimated |

## 13. 当前限制与后续边界

| 限制 | 当前范围 |
| --- | --- |
| 恢复探针只在当前进程内互斥 | [RoutingEngine](../src/rotor/gateway/routing.py) 的冷却、探针占用及 adaptive 统计驻留内存；多个 worker 不是全局单探针，进程重启也不保留这些状态 |
| 恢复检查依赖业务请求 | 冷却到期只允许后续请求探测，没有定时后台健康检查；日期 Retry-After 的初始解析仍依赖本机墙上时钟 |
| 租约复评需要明确来源 | [session_leases.py](../src/rotor/services/session_leases.py) 遇到最新事件缺少成功 attempt、协议证据不完整，或 `assigned/index=0` 且无故障来源时保留原 lease；这一限制也适用于新记录，不仅是旧历史数据 |
| 租约仍按 session/model 共享，协议族按渠道声明判断 | 复评不会自动改变 `previous_response_id` 归属；不会仅因增加了更高优先级渠道就迁移正常 lease。Zhipu 的有效原生路径不自动改写 `channel.protocol` 的亲和分组 |
| 协议扩展仍有显式边界 | 原生 guard 覆盖已识别语义，未知 Chat 顶层字段仍可能被 schema 忽略；可选 hosted tools 的降级目前只有日志，没有策略开关 |
| Responses → Chat 的 reasoning/refusal 与请求字段仍待后续处理 | 本批仅修完成状态、失败判定和用量一致性，不补齐这些反向语义映射或扩大请求字段保留范围；不能据此宣称协议转换无损 |
| Responses GET 流仍是原始 relay | 后台终态记账已按成功/失败区分，但 GET 流没有复用 POST 生成流的严格解析与终态校验 |
| Anthropic 原生与跨协议保真范围不同 | 原生未知扩展仍可透传，未知 stream 增量只以原事件归档；跨协议只对 §6 明确列出的不可表达语义拒绝，未宣称覆盖所有未来字段 |
| 目录与计数不是生成健康证明 | 本地 Models 目录不探活，管理目录探测不调用生成；estimated 计数不是供应商 tokenizer 结果，provider 计数也不会直接解除生成恢复探针 |
