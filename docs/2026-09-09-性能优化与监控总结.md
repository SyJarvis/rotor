# Rotor 性能优化与监控总结

日期：2026-09-09。本文汇总数据库优化、网页监控、Responses 误报修复、MindCode 来源识别与推理参数透传的当前状态。

## 1. 当前结论

本轮工作优先保证记账正确，再减少事务提交，并建立可用于后续优化的观测入口。

- Token 累计采用数据库原子更新；事务收尾覆盖已 flush 和 Core DML 的写入。
- 后台归档合并连续数据库事件，隔离基准中每 100 请求的提交尝试次数减少约 27%。
- 管理网页增加「监控 → 性能」，展示数据库、协议请求、存档队列及增量对账。
- 已修复超大 Responses 完成事件导致的失败误报；旧监控数字不能直接当作上游成功率。
- 已加入 MindCode 来源识别，客户端仍需发送约定请求头。
- 已确认 Responses 原生请求保留推理配置；这不等于已经完成模型能力全面无损的验证。

用户已部署过此前优化，但本文不据此推定后续修复已在运行。当前代码已经验证，尚未确认本地运行服务加载的具体版本，也未在本轮操作中重启服务。

## 2. 数据库与归档优化

| 项目 | 当前行为 | 正确性边界 |
|---|---|---|
| Token 记账 | 请求数、token 数与已用额度在数据库内原子累加，与账本同事务；额度禁用判断使用数据库当前值，保留已禁用状态 | 保证已记账用量累计，不提供请求执行前的并发硬额度预留 |
| 事务收尾 | `get_db` 正常退出且仍有事务时提交；异常回滚，取消期间完成清理 | 已显式提交且未开启新事务时不重复提交；不能仅凭 ORM 脏集合判断是否需要提交 |
| 会话 lease | 默认空闲有效期 30 分钟；成功请求刷新最近使用时间和到期时间，同渠道续期不重复写事件 | 已保存设置不会自动覆盖；模型、渠道的显式配置仍优先 |
| 后台批次 | 连续 `db_only` 事件每批最多 32 条，一批一次提交；文件事件独立处理 | 不跨文件事件合批，不改变事件顺序 |
| 失败重试 | 整批失败先回滚，再按原顺序逐项重试；已成功追加文件的事件保留进程内标记 | 数据库重试不重复追加已确认写入的文件，但不保证文件与数据库跨崩溃原子性，也不能消除部分文件写入后 I/O 报错的不确定性 |
| 排空 | `drain()` 等待排队和处理中事件，包括重试，报告超时或 worker 异常 | 队列长度为零不等于后台提交完成 |

数据库引擎工厂统一生产与基准配置，SQLite 保留 WAL、`busy_timeout=5000` 和 `synchronous=NORMAL`。本轮没有通过扩大连接池来宣称性能收益。

Anthropic 流式结束顺序也已修正：成功记账事务提交、存档事件入队之后，才发送 `message_stop`，避免客户端收到终态立即断开导致记账被取消。存档入队不表示文件已落盘。

实现依据：[数据库会话](../src/rotor/database.py)、[记账](../src/rotor/gateway/accounting.py)、[会话 lease](../src/rotor/services/session_leases.py)、[归档 worker](../src/rotor/conversations/store.py)、[Anthropic 端点](../src/rotor/api/v1/anthropic.py)。

## 3. 已验证的性能收益

使用校准后的同一脚本，同机各运行三轮 Chat 非流式测试：并发 8、测量 100 请求、预热 5 请求，独立临时 SQLite 与存档目录。对比仅替换后台归档 worker，预热后和测量后均排空后台工作。

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 每轮 Engine commit 尝试次数 | 400 / 400 / 400 | 293 / 292 / 292 |
| RPS | 150.9 / 155.5 / 145.3 | 157.5 / 168.3 / 163.9 |
| 请求延迟 p95（毫秒） | 267.3 / 146.1 / 192.3 | 213.9 / 156.2 / 202.3 |
| 成功请求 | 每轮 100 | 每轮 100 |

提交尝试次数减少约 **27%**，SQL 操作数保持一致。六轮的账本、请求日志、Token 累计及归档完整性检查均一致。

RPS 中位数从 150.9 到 163.9，仅代表同机短压测观察；p95 在部分轮次上升，不能宣称尾延迟已经改善，也不能外推生产吞吐收益。

基准直接统计 SQL、提交事件与连接持有时间，后者不能当作连接获取等待。流式 TTFT 使用网关与模拟上游的真实 HTTP 连接验证，进程内 transport 不报告 TTFT，避免缓冲造成错误结论。

具体参数、历史口径修正与复现命令见 [DB 读写性能优化记录](DB读写性能优化记录.md)，脚本见 [bench_gateway.py](../scripts/bench_gateway.py)。

## 4. 网页监控如何使用

管理网页入口为 **「监控 → 性能」**，同页保留「会话来源」。自动刷新默认关闭，启用后约每 10 秒刷新；离开页面、隐藏页面或认证失效时停止轮询，避免后台重复请求。

| 指标 | 含义与读法 |
|---|---|
| 数据库连接获取 | 完整连接获取耗时，可能包含连接创建与检查，不是纯连接池排队时间 |
| SQL / commit / 连接持有 | 分别观察语句执行、实际提交调用、checkout 到 checkin 的耗时，不能混为一个等待指标 |
| 协议成功 / 失败 / 取消 | 当前进程启动以来的累计分类；仅统计推理端点，不包含管理网页请求 |
| 请求耗时 | 非流式至响应结束；流式以已发送终态为完成依据，终态后客户端断开不应改判取消 |
| 首字延迟 TTFT | 首个非空文本增量发送时间；角色、工具参数和图片不算首字，无文本时不强填零 |
| 存档队列 | 队列深度、丢弃事件数，以及批大小、处理耗时、排队等待与排空耗时 |
| 增量对账 | 比较基线后成功账本与 Token 请求数、token 数、已用额度的增量 |

耗时分位数保留最近 **300 秒、每个序列最多 2048 个样本**；流量超过上限时，仅保留最新样本。页面的 `n` 表示窗口内实际保留的样本数，累计次数则从进程启动起计算。因此累计成功率和耗时 p95 不一定覆盖相同请求集合，`n=2` 也不足以判断稳定性能趋势。

指标在有界内存中保存，重启会清零，不新增指标数据库写入；既有管理认证可能按原逻辑更新会话活动时间。指标不保存请求正文、SQL 文本或密钥。

性能计数属于**单进程**，网页展示 PID 与启动时间。多 worker 请求可能落到不同进程，不能把一次页面查询视为全局汇总，也不能混用不同 PID 的性能统计与对账基线。

实现依据：[指标与对账](../src/rotor/observability.py)、[请求观测](../src/rotor/core/middleware.py)、[管理 API](../src/rotor/api/admin/monitoring.py)、[性能页面](../src/rotor/frontend/pages/performance.js)。

### 增量对账的边界

首次检查建立 Token 快照和账本 ID 基线；后续只聚合游标之后新增的成功账本，并在同一 SQLite 读取快照中比较累计增量。检查结果缓存 30 秒，不会因每次网页刷新而扫描全部历史账本。

- `baseline`：刚建立基线，尚不能证明历史数据一致。
- `ok`：基线之后的增量一致。
- `mismatch`：增量不同，可能是记账差异或人工修改累计值，需要核查。
- `invalid`：Token 集合、额度或身份发生变化，计数下降或账本 ID 回退等使基线失效。
- `error`：无法完成检查，不能解释为对账成功。

重建基线仅重置内存中的比较起点，**不会修账，也不会消除既有历史差异**。此功能目前只支持 SQLite，其他数据库返回不支持状态；本轮监控不需要数据库 schema 迁移。

## 5. Responses 失败误报及修复

曾出现网页 Responses 显示成功 5、失败 27、取消 2，成功率 14.71% 的情况。页面按 `5 / (5 + 27 + 2)` 计算，取消也包含在分母；对应耗时的 `n=2` 是最近 300 秒保留的两个样本，不是这 34 次累计请求。失败包含 HTTP 错误、流错误或未识别终态等情况，不能直接解释成上游可用性。

本地数据库历史核查记录显示：2026-09-09 北京时间 **08:00–09:36**，Responses 已入账请求成功 210 次、失败 1 次；唯一失败在 09:32:04，为上游 502。该时间范围与进程内监控窗口不同，且鉴权等失败可能没有账本，不能断言全部 27 次都是同一个缺陷。

确认的实现缺陷是：观测器为限制内存，对超过 **64 KiB** 的 SSE 事件丢弃解析数据；大型 `response.completed` 事件也被丢弃，正常响应因“未看到完成事件”被判为失败。较长输出或较大工具参数可触发这一场景。

修复后，普通事件继续使用原解析路径；超大 Responses 事件使用有界增量解析器验证 JSON 结构，仅保留根字段 `type`、`error` 等判断所需状态，跳过长正文和参数。既保持内存限制，也能识别完成、失败与不完整终态；不修改客户端收到的原始响应字节，不新增数据库写入。

隔离真实 HTTP 复现结果：

| 项目 | 修复前 | 修复后 |
|---|---|---|
| 实际完成请求 | 6 | 6 |
| 监控分类 | 成功 0、失败 6 | 成功 6、失败 0 |
| 增量对账 | 6 请求、66 tokens，一致 | 6 请求、66 tokens，一致 |

这证明该误报路径已经修复，不意味着真实上游 502 应被忽略。失败原因进一步细分展示尚未实现。

实现与回归：[超大事件解析器](../src/rotor/core/_response_event.py)、[网关监控测试](../tests/test_gateway_metrics.py)。

## 6. MindCode 会话来源

Rotor 已支持请求头 `x-mindcode-session-id`，并在「监控 → 会话来源」增加 MindCode 分类。Chat 协议可直接在 `/v1/chat/completions` 请求中附带：

```http
x-mindcode-session-id: 当前会话的唯一ID
```

同一会话的多轮请求、工具调用、重试复用同一个 ID；新会话生成新 ID，恢复会话继续使用原 ID。普通与流式请求都适用。

显式 `x-conversation-id`、`x-rotor-session-id` 优先级更高；同时发送时会优先采用它们，不能期待请求仍按 MindCode 头归类。

此前对 `~/base` 安装版的核查未观察到该客户端发送约定来源与会话头，客户端仍待接入；其 CLI 依赖问题也未在本轮修复。因此“Rotor 支持识别”不等于现有 MindCode 请求已经自动归类。

实现与验证：[会话身份解析](../src/rotor/core/client_session.py)、[会话身份测试](../tests/test_client_session.py)、[监控接口测试](../tests/test_admin_monitoring.py)。

## 7. Codex 与推理强度透传

对 Responses 原生请求，Rotor 保留客户端提交的推理配置，例如：

```json
{
  "reasoning": {
    "effort": "xhigh",
    "summary": "auto"
  }
}
```

携带推理配置的 Responses 请求要求原生 Responses 渠道，避免降级转换时丢失参数。Chat 请求转换为 Responses 上游时，`reasoning_effort` 映射为 `reasoning.effort`；客户端没有提交该字段时，不擅自强制高推理强度。

相关测试检查实际发往模拟上游的请求体，覆盖流式与非流式。结论是**网关保留推理参数**，不保证上游实际执行，也不能单凭这个字段宣称“模型能力完全没有打折扣”。模型映射、输出上限、上下文与工具参数的完整保真仍需单独核对。

实现与验证：[Responses 适配器](../src/rotor/adapters/protocol/responses.py)、[协议回归测试](../tests/test_responses_protocol.py)。
