# Rotor 实现路线图

本文档记录 Rotor 的主要演进方向。具体设计和接口以对应设计文档为准，
路线图中的阶段顺序可根据生产问题和用户需求调整。

## P0：网关生产化基础

- [x] 为管理页面和 `/api/admin/*` 增加管理员鉴权、登录限流与认证审计。
- [ ] 对上游 API Key 和 Rotor Token 做安全存储与响应脱敏。
- [x] 补齐并验证 SQLite Alembic 迁移链，启动不再依赖 `create_all` 升级数据库。
- [ ] 验证 SQLite 与 PostgreSQL 双数据库兼容性。
- [ ] 实现 Channel RPM、TPM、并发限制和原子配额更新。
- [ ] 整理单元测试与真实集成测试，接入 CI。

## P1：结构化模型卡与基础知识库

目标是让 Rotor 能可靠回答“模型支持什么”，并让路由在调用上游之前完成
模态、任务和接口能力匹配。详细方案见
[模型卡与模型能力知识库设计](model-cards-design.md)。

- [ ] 定义并版本化 `ModelCard` Schema。
- [ ] 建立仓库内置模型目录，优先覆盖当前已配置模型。
- [ ] 区分输入/输出模态、任务能力、接口特性和使用限制。
- [ ] 将 OCR、视觉问答、文档理解等建模为任务能力，而不是简单的“多模态”标签。
- [ ] 保存每项能力的来源、验证时间、支持状态和可信度。
- [ ] 支持官方模型卡、Channel 覆盖和实际探测结果的分层合并。
- [ ] 为管理页面增加模型卡查看、编辑、来源和过期状态展示。
- [ ] 提供模型卡查询、能力筛选、比较和推荐 API。
- [ ] 从请求内容提取能力要求，并接入 Rotor 路由过滤与错误说明。
- [ ] 为 MindAgent 注册确定性的模型查询、比较、推荐和路由解释工具。
- [ ] 将 Provider 文档、最佳实践和已知问题作为第二层可检索知识库。

### P1 验收目标

- 图片请求不会被路由到已知的纯文本模型。
- 未知能力不会被默认视为支持。
- 同一个模型可在不同 Channel 上拥有不同的有效能力。
- 每个路由能力结论都能追溯到模型卡、人工覆盖或探测记录。
- Rotor Agent 能解释模型选择依据，而不是根据模型名称猜测。

## P2：MindAgent 深度集成

- [ ] 建立用户身份、会话和 Rotor Token 的明确归属关系。
- [ ] 注册经过沙箱和权限控制的文件、搜索、执行与记忆工具。
- [ ] 接入模型卡查询与模型推荐工具。
- [ ] 支持长会话上下文管理、任务状态和可恢复执行。
- [ ] 支持人工审批、执行边界和工具调用审计。
- [ ] 在模型能力不足时推荐可用模型或 Channel。

## P3：MCP 与 Skill 生态

- [ ] 对接外部 MCP 服务，例如网页搜索和专业数据源。
- [x] 让 Rotor 暴露自己的只读 stdio MCP Server，并完成 Codex、Claude Code E2E。
- [ ] 提供 Skill 查询、下载、安装包获取和版本信息。
- [ ] 支持通过 GitHub 地址、压缩包等方式分发 Skill。
- [ ] 将模型卡查询暴露为 MCP 工具。
- [x] 将当前安全 Channel 列表和详情查询暴露为 MCP 工具。
- [x] 将请求 trace、近期失败和模型用量查询暴露为 MCP 工具。

## P4：持续评估与自动维护

- [ ] 构建模型能力探测矩阵和可重复的 Mock/真实上游测试。
- [ ] 定期检查模型卡来源是否过期。
- [ ] 对模型能力变化生成差异报告，人工审核后更新内置目录。
- [ ] 基于实际路由结果评估模型卡准确性和 Channel 能力差异。
- [ ] 建立模型质量、延迟、成本和可用性的评测数据，为推荐策略提供依据。
