# Rotor 提交拆分指南

> 现状：本地工作区有 **49 个文件改动（+4358 / −1041）**，加上 **12 个未跟踪源码文件（~1704 行）** 和若干 docs/examples/scripts。规模超过已提交代码总和，一次性提交无法 review。
>
> 本方案按**功能主题**拆为 10 个 commit，按依赖顺序排列，每步给出 `git add` 清单和提交命令，可直接顺序执行。

---

## 拆分原则

1. **基础设施先行**：清理/重构/数据库层先于业务功能。
2. **DB schema 与 ORM model 同 commit**：迁移文件与对应 model 不拆开。
3. **跨 feature 文件按 hunk 拆分**：`main.py`、`config.py`、`database.py` 等被多个 feature 共用的文件，按 hunk 分别 stage（用 `git add -p`）。
4. **测试随实现一起提交**：同一 feature 的 test 与源码同 commit，便于后续 bisect。
5. **docs 单独成 commit**：避免污染代码 review。

## 执行顺序与回滚

按 Step 1 → 11 顺序执行即可。若中途发现某个 commit 内容错了：

```bash
# 撤销最近一次 commit 但保留改动
git reset --soft HEAD~1

# 撤销 commit 并取消 stage
git reset --mixed HEAD~1
```

> **不要**用 `git reset --hard` 或 `git push --force`，工作区有大量未提交内容。

## 常见坑

1. **`git add -p` 漏 hunk**：`main.py` 被 3 个 commit 共用（Step 3 / 8 / 间接被 5、6 通过 import 影响），每步只 stage 该步骤相关的 hunk。建议每次 `git add -p` 后用 `git diff --cached src/rotor/main.py` 复核。
2. **alembic 迁移链断裂**：Step 5 与 Step 6 的两个迁移文件 `down_revision` 必须首尾相接，确认顺序：`7f2c9a3e1b4d` → `8c4f1a2b3d5e` → `a1b2c3d4e5f6`。
3. **未跟踪的中文文件名**：含 emoji/中文路径在 macOS 终端默认 NFD 编码下可能与 NFC 表现不同，若 `git add` 报路径不存在，先 `git config core.quotePath false`。
4. **`__pycache__`**：`alembic/versions/__pycache__` 与 `examples/__pycache__` 不应入库，确认 `.gitignore` 已覆盖。
