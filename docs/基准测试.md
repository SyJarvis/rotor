、# Rotor API 网关基准测试方案

## 1. 测试目标

基准测试用于回答：

1. Rotor 相比直连上游增加了多少延迟。
2. 不同并发量下能稳定处理多少请求和流式连接。
3. OpenAI Chat、OpenAI Responses 和 Anthropic Messages 是否行为一致。
4. 请求日志、Token 用量与配额累计是否准确。
5. 上游超时或失败时，路由切换是否有效。

测试代码统一使用官方 Python SDK：

- `openai`：测试 Chat Completions 和 Responses API。
- `anthropic`：测试 Anthropic Messages API。

调用格式参考：

- [`examples/openai_example.py`](../examples/openai_example.py)
- [`examples/openai_responses_example.py`](../examples/openai_responses_example.py)
- [`examples/anthropic_messages_example.py`](../examples/anthropic_messages_example.py)

并发测试使用 `AsyncOpenAI` 和 `AsyncAnthropic`，避免同步客户端线程池影响结果。

## 2. 测试矩阵

| 协议 | Rotor 入口 | 非流式 | 流式 |
|---|---|---:|---:|
| OpenAI Chat | `/v1/chat/completions` | 必测 | 必测 |
| OpenAI Responses | `/v1/responses` | 必测 | 必测 |
| Anthropic Messages | `/anthropic/v1/messages` | 必测 | 必测 |

每种组合覆盖：

- 单请求正确性
- 固定请求数并发
- 固定时间持续压测
- 长上下文
- 上游错误和超时

## 3. 测试环境

### 3.1 可控 Mock 上游

Mock 服务返回固定内容和固定 Token usage，并可配置：

- 首包延迟
- 流式 chunk 间隔和数量
- HTTP 429、500、503 错误率
- 请求超时

该场景用于测量 Rotor 自身开销及 Token 统计准确性，避免真实模型波动干扰结果。

### 3.2 真实模型上游

使用固定模型、参数和提示词测试实际调用下的稳定性、路由和长连接表现。真实模型结果不用于衡量微小的网关开销。

### 3.3 直连对照

同一组请求分别执行：

```text
客户端 -> 上游 API
客户端 -> Rotor -> 同一个上游 API
```

两组测试保持模型、提示词、最大输出、流式设置、并发数、请求数、客户端机器和网络一致。

```text
overhead_p50 = rotor_p50 - direct_p50
overhead_p95 = rotor_p95 - direct_p95
overhead_p99 = rotor_p99 - direct_p99
```

不应只比较平均延迟。

## 4. 指标

### 4.1 请求指标

- 请求总数、成功数、失败数和错误率
- RPS 和成功 RPS
- 总延迟 P50、P90、P95、P99 和最大值
- HTTP 状态码与错误类型分布

### 4.2 流式指标

- TTFT：发出请求到收到首个有效文本事件
- 完整响应时间
- chunk 数量和相邻 chunk 间隔
- 输出 Token/s
- 客户端中断和服务端流错误数量

仅收到 HTTP 200 不代表流式请求成功。测试程序必须完整消费响应流并收到协议结束事件。

### 4.3 Token 与记账指标

每轮测试前后记录：

- SDK 响应中的 usage
- `RequestLog` 增量
- `UsageLedger` 增量
- API Key 的 `used_quota` 增量
- 渠道请求数增量

成功请求应满足：

```text
SDK total_tokens
= RequestLog.total_tokens
= UsageLedger.total_tokens
= used_quota 增量
```

流式请求必须完整读取到结束，否则服务端流式生成器可能尚未提交记账。

### 4.4 系统指标

- Rotor 进程 CPU、常驻内存和峰值内存
- 活跃连接数
- 数据库写入耗时
- SQLite 锁错误或 PostgreSQL 连接池等待

SQLite 和 PostgreSQL 分别测试，报告必须标明数据库类型。

## 5. 建议测试档位

### 5.1 冒烟测试

三种协议的流式和非流式各执行一个请求，验证响应结构与 Token 记账。每次正式压测前运行。

### 5.2 并发阶梯

| 档位 | 并发数 | 请求数 |
|---|---:|---:|
| 单用户 | 1 | 20 |
| 低负载 | 10 | 200 |
| 中负载 | 50 | 1,000 |
| 高负载 | 100 | 2,000 |
| 压力测试 | 从 200 逐步增加 | 每档至少 2,000 |

每档先预热，再独立运行至少三轮，报告使用三轮中位数。

### 5.3 稳定性测试

- 持续 30 分钟起
- 使用稳定容量的 50% 和 80% 并发
- 观察错误率、内存增长、数据库积压和连接泄漏

### 5.4 故障转移测试

准备两个支持同一模型的渠道：

1. 正常发送流量。
2. 让首选渠道返回 503 或超时。
3. 记录故障检测和切换时间。
4. 验证请求只记账一次。
5. 恢复渠道并观察后续路由。

## 6. 测试程序设计

建议目录：

```text
benchmarks/
  README.md
  config.example.yaml
  runner.py
  clients.py
  metrics.py
  validate_usage.py
  mock_provider.py
  report.py
  scenarios/
    smoke.yaml
    concurrency.yaml
    stability.yaml
    failover.yaml
  results/
```

文件职责：

- `clients.py`：封装 `AsyncOpenAI` 和 `AsyncAnthropic`。
- `runner.py`：控制并发、预热、轮次和超时。
- `metrics.py`：计算分位数、RPS、TTFT 和 Token/s。
- `validate_usage.py`：查询管理接口或数据库，校验记账。
- `mock_provider.py`：提供可重复的上游响应。
- `report.py`：生成 JSON 原始结果和 Markdown 报告。

并发控制使用 `asyncio.Semaphore`。每个请求保留独立结果，不能只记录全局成功数，否则无法分析长尾和单次记账偏差。

## 7. 配置与结果

沿用 `examples` 环境变量：

```bash
export ROTOR_API_KEY="sk-..."
export ROTOR_BASE_URL="http://127.0.0.1:8000"
export ROTOR_MODEL="glm-5.2"
```

直连对照配置：

```bash
export UPSTREAM_API_KEY="..."
export UPSTREAM_BASE_URL="https://provider.example/v1"
export UPSTREAM_MODEL="provider-model"
```

敏感信息不得写入配置模板和测试结果。报告仅保留脱敏地址、渠道 ID 和 Key ID。

每轮输出：

```text
benchmarks/results/<timestamp>/
  environment.json
  raw-results.jsonl
  summary.json
  report.md
```

`environment.json` 至少记录：

- Git commit
- Rotor、Python、`openai`、`anthropic` 版本
- 操作系统和 CPU
- 数据库类型
- 场景参数
- Rotor 配置摘要

## 8. 第一阶段验收标准

- 三种协议的流式和非流式全部通过冒烟测试。
- 100 并发下无请求日志丢失。
- SDK usage 与 Rotor 记账无差异。
- 正常负载下网关 P95 额外开销可稳定复现。
- 流式请求无异常中断，TTFT 可独立统计。
- 30 分钟测试无持续内存增长。
- 上游故障时能切换渠道且不会重复计费。

具体性能阈值应在获得第一轮可重复数据后确定，不在缺少硬件、数据库和上游基线时预设。
