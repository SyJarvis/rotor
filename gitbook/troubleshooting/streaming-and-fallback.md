# 流式响应与故障转移

流式请求的故障时机决定 Rotor 是否能够安全切换渠道。

## 首字节之前失败

如果连接、认证、限流或上游服务器错误发生在 Rotor 向客户端发送首个 SSE 字节
之前，且错误满足 fallback 条件，Rotor 可以关闭当前上游响应并尝试下一个候选。

检查响应头：

```text
X-Rotor-Channel
X-Rotor-Fallback: true
```

如果没有候选渠道，检查模型、协议、能力、Token 渠道限制和渠道启用状态。

## 首字节之后失败

响应流开始后，客户端可能已经收到部分文本或工具调用。Rotor 无法把新渠道的完整
响应无缝拼接到已有流中，也不能保证重新请求没有副作用。因此，首字节后的失败会
结束当前流，而不是透明 fallback。

客户端应把此情况当作一次失败的生成请求，根据业务幂等性决定是否重新发起。

## 上游没有返回 usage

Rotor 会等待流尾的 usage 事件。若供应商没有发送，usage ledger 将
`usage_source` 记录为 `missing`，Token 数量保持为零，不会用本地估算冒充上游
数据。

## 诊断步骤

1. 用非流式请求验证相同模型和内容；
2. 查看请求日志中的错误码和清理后的供应商响应；
3. 查看 `X-Rotor-Channel`，确认实际渠道；
4. 对该渠道运行模型发现测试；
5. 检查是否只有流式协议、工具事件或 usage 尾块失败；
6. 使用另一个独立渠道验证 fallback 候选集。

协议转换问题还应对照[协议兼容与转换](../concepts/protocols.md)。
